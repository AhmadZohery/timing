# OPP-0101: Multi-Device Conflict-Free Delta Sync Engine

## 1. Problem Statement
Midmar LifeOS currently syncs by taking a full database export JSON dump (`/api/sync/backup`) and overwriting or restoring it in the companion server's `data/backup-latest.json` or PostgreSQL. If a user logs habits on their phone during a commute and completes work tasks on their desktop, restoring or syncing either device risks overwriting the other device's changes.

## 2. Evidence Base
- Code inspection: `src/services/serverSyncService.ts` currently sends entire table snapshots.
- `server/index.mjs` has `/api/sync/backup` which writes a monolithic JSON payload.
- Logged Risk: `RISK-0003` in `project-management/state/risks.jsonl`.

## 3. Counter-Evidence & Risks
- Building a full distributed CRDT engine (e.g. Yjs, Automerge) adds significant bundle weight (~150-250KB) and architectural complexity.
- Potential performance impact on low-end mobile devices during large sync merges.

## 4. Alternatives Considered
- **Alternative A (Lightweight Last-Write-Wins):** Add `updatedAt` and `isDeleted` tombstones to every Dexie table. Sync only records where `updatedAt > lastSyncTimestamp`. Simple, zero additional library dependencies.
- **Alternative B (Full Yjs CRDT):** Overkill for structured relational tables like prayer logs or habit counters.

## 5. Technical Architecture
1. Introduce Dexie Schema v12 with compound index `[userId+updatedAt]` and `isDeleted` flag on tables.
2. Endpoint `/api/sync/delta`:
   - Client sends `{ lastSyncTimestamp, changes: { table: [records] } }`.
   - Server merges into PostgreSQL using `ON CONFLICT (id) DO UPDATE WHERE EXCLUDED.updated_at > current.updated_at`.
   - Server returns server-side changes since `lastSyncTimestamp`.

## 6. Success Metrics
- Zero data loss across simultaneous desktop and mobile usage.
- Sync payload reduced by >90% compared to monolithic JSON export.
